# Oakhollow: rules for working on this codebase

A village simulation. Browser game in `public/`, tiny Node server in `server.js`.
All game code lives in `public/src/`, split into layers. Read this before changing anything.

## Commands

- `npm start`: run the game at http://localhost:3000 (`?offline` = no API calls)
- `npm run verify`: **run before finishing any change**: all lints, then all tests
- `npm test`: tests only (about 2s). `npm run lint`: all lints (`lint:arch` architecture rules, `lint:js` ESLint,
  `lint:md` Markdown formatting).
- `npm run docs:build`: regenerate `docs/reference/` from the code. `npm run format:md`: format Markdown with Prettier.
- `npm run report:deps`: module sizes and import cycles. `npm run setup:hooks`: enable the pre-commit hook.
- `npm run demo:record`: record the demo video to `recordings/` (needs Chrome and ffmpeg; see `docs/how-to.md`).

## Hard rules (enforced by `npm run lint`, the pre-commit hook and CI)

1. **Files ≤ 200 lines.** When a file grows past that, split it by responsibility. Don't just move code to a random file.
2. **Functions ≤ 80 lines** and **complexity ≤ 25**. Extract named helpers; use lookup tables instead of long `switch`/`if` chains.
3. **No import cycles.**
4. **Layers only import downward.** From bottom to top:
   `data` → `core` → `identity`, `nav`, `economy` → `social` → `world`, `life`, `village` → `effects` → `actions` → `ai` → `ui` → `app`.
   If a lower layer must trigger something above it, emit an event (`core/events.js`) and let the higher layer listen.
5. **Registries, not switches.** New verbs register via `defineVerbs()` (`actions/registry.js`); new effect types via `defineEffect()` (`effects/registry.js`); new option providers are added to `ai/options/index.js`.
6. **Hosts use the public API.** The UI, tests and tools import from `public/src/api.js` (or the layer's `index.js`).
7. **No exceptions.** All code meets these rules. Don't add `eslint-disable` comments or a suppressions baseline: fix the code instead.

## Where things go

| Adding...                                                            | Put it in                                               |
| -------------------------------------------------------------------- | ------------------------------------------------------- |
| Static world content (places, people, activities, prices)            | `data/`                                                 |
| Something every system needs (state, memory, time, events)           | `core/`                                                 |
| How people relate, talk, promise, request                            | `social/`                                               |
| Biology, family, health, death, gatherings                           | `life/`                                                 |
| Village-wide systems (problems, politics, economy days, storyteller) | `village/`                                              |
| A new building block for inventions                                  | a `defineEffect` in `effects/types/`                    |
| A new thing people can do                                            | a verb in `actions/verbs/` + an option in `ai/options/` |
| How minds decide (Jev), speak or invent                              | `ai/`                                                   |
| Drawing and panels                                                   | `ui/`                                                   |

Each file starts with a one-line comment saying what it's for. Keep that line accurate.

## Testing

- **Golden master** (`tests/golden.test.mjs`): replays two game days on three fixed seeds and compares a fingerprint
  of the world. Pure refactors must keep it passing unchanged. If you _intend_ to change behaviour, regenerate it
  with `npm run test:update-golden` and say so in your summary.
- Add a focused test in `tests/` for every bug you fix (see the regression tests in `tests/life.test.mjs`).
- Tests run headless and offline with a seeded random generator (`tests/harness.mjs`); no network, no browser.
- **UI smoke tests** (`tests/ui.test.mjs`) draw the map and fill every panel headless, using the fake canvas and DOM in
  `tests/fake-dom.mjs`. They catch crashes, NaN coordinates and `undefined`/`NaN` in panel text, but not how things
  look, so visual changes still need a glance in the browser.
- Code that only runs with live AI (prompts, `buildState`) isn't covered by the offline golden master. When
  refactoring it, compare old and new outputs (differential testing) before trusting the change.

## Documentation

- The docs follow [Diátaxis](https://diataxis.fr/): `docs/tutorial.md`, `docs/how-to.md`, `docs/reference/`,
  `docs/explanation/`. Put new material in the one kind of page it belongs to; don't mix them.
- `docs/reference/effects.md`, `verbs.md` and `world.md` are generated by `tools/docs.mjs`. Don't edit them; run
  `npm run docs:build` after changing effects, verbs or `data/`. The tests fail if they are stale.
- When behaviour changes, update the page that describes it in the same change.
- Write short, plain sentences. No marketing or filler words (`simply`, `powerful`, `seamless`...) and no
  exclamation marks; `tests/docs.test.mjs` rejects them, and checks that relative links resolve.
- Keep the README to what a newcomer needs to run the game; link to `docs/` for the rest.

## Conventions

- Plain ES modules, no build step, no runtime dependencies. Dev tools only (ESLint).
- Use each person's pronouns via `identity.js` (`P(npc).their`, `fill('{They} {are}...', npc)`), never hard-coded "their".
- Follow current practice: check the latest stable versions (Node LTS, ESLint, GitHub Actions) before adding or upgrading
  tooling, and prefer built-ins (`node:test`, `structuredClone`, flat ESLint config) over extra dependencies.
- Never commit `.env`: it holds API keys. A new environment variable goes in `.env.example` and
  `docs/reference/configuration.md` too (`tests/config.test.mjs` checks this).
